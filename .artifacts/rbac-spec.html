Who Can Do What

The IT Asset Management platform recognizes four roles, defined once as a Postgres enum (db/001_schema.sql) and enforced identically at every API route via requireRole(). This is a description of the code as it runs today, not an aspiration.

The Four Roles

Ordered by operational reach, not hierarchy of pay grade — a MANAGER sees more than an EMPLOYEE but can change nothing an EMPLOYEE can't.

Tier 0 — Fleet user EMPLOYEE

Custodian of whatever is checked out to them. Can accept an OTP handshake, return or report their own asset lost. No visibility into anyone else's assets or the audit trail.

Tier 1 — Observer MANAGER

Everything an EMPLOYEE can do, plus read access to the audit timeline, ops KPIs, and open recovery tasks. Cannot trigger a single state change beyond their own custody.

Tier 2 — Operator ASSET_ADMIN

Runs the fleet: checkout, inspection, recovery, sweeps, offboarding, org policy, user provisioning, and asset intake. Everything operational lives behind this role.

Tier 2 — Operator SUPER_ADMIN

Identical permission set to ASSET_ADMIN in the current codebase — reserved for a future distinction (e.g. billing, cross-org actions) that hasn't been built yet.

Read Before You Rely On This

own Ownership check, not a role check. "Return" and "report lost" grant EMPLOYEE only over the asset currently checked out to them — enforced by an explicit current_holder_id comparison inside the route, on top of the role gate.
· MANAGER is read-only. It exists entirely to see the timeline and ops dashboard — every write action in the matrix skips straight from EMPLOYEE to ASSET_ADMIN.
· ASSET_ADMIN and SUPER_ADMIN are currently identical. No route distinguishes between them yet; the second tier is provisioned for a future capability, not a present one.
· Every grant above is also scoped by tenant. Postgres row-level security keys every query to the caller's org_id — a role check answers "can this action happen," RLS separately answers "on whose data."
